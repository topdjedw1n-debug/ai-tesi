## Що виправлено під час релізної перевірки

1. Оператор більше не може підміняти службові статуси, оплату чи витрати
   через PATCH. Доступ до власних вимог збережено. Вісім негативних
   перевірок відтворили порушення до виправлення; після нього проходять.
2. Пізня відповідь про прогрес не стирає назву розділу й оцінку часу,
   не відсуває живий прогрес назад і не відкриває вже завершену задачу.
3. Збереження однієї перевірки зберігає незавершене введення в інших
   формах. Новий fingerprint DOCX, як і раніше, очищає стару форму.
4. Відхилене завантаження не робить зайвий запис, якщо інша транзакція
   вже відкликала дозвіл, поки запит чекав блокування.
5. Релізний скрипт підключає конфігурацію встановленого бота й зберігає
   його приватну мережу. Відсутня конфігурація або невалідний Compose
   зупиняють скрипт до змін. Перезапускаються тільки API/web, без залежностей.
6. Виправлено три нові помилки типів фільтрів, виявлені порівнянням саме
   з серверною базою, а не лише з попереднім локальним етапом.

Нових міграцій і змін продуктових порогів немає.

Свіжий API-образ зібрано з Dockerfile: 109/109 файлів його app збігаються
з кандидатом, SDK-контракти виконуються, приватних `.env` немає.
Локальна архітектура arm64; перед серверною активацією потрібна збірка
й ті самі перевірки в середовищі сервера. Ідентифікатори контейнерів,
окремі перевірки зібраних образів і build ID наведені в JSON.
HTTP-перевірка web підтверджує запуск контейнера та сторінок; вона не є
входом під обліковим записом Тані чи її прийманням роботи.

GitHub CI цього незакоміченого пакета не запускався. Workflow обмежено
main/develop/production; локальні перевірки не називаємо зеленим GitHub CI.

Початкові невдалі спроби перевірок збережені: production URL у тесті з
очікуваним localhost, відсутній fetch у jsdom, відсутній тестовий SECRET_KEY,
неповна локальна CA-конфігурація Python та завислий Docker credential helper.
Вони усунені в середовищі перевірки; TLS не вимикали, залежності не змінювали.
Ізольована Docker-мережа не публікувала тестовий web-порт; той самий образ
перевірено в локальній bridge-мережі з портом лише на 127.0.0.1. Для входу
використано наявний маршрут `/auth/login`; початковий `/login` повертав 404.

## Конкретна активація після погодження фаундера

1. Відтворити кандидата з бази й патча в окремому checkout; звірити SHA-256
   кожного файла з JSON. Коміт містить тільки цей пакет і релізні докази.
2. Повторно перевірити відсутність активних задач і незмінність сервера.
   Якщо після цього знімка з'явилися записи, зробити свіжі копії перед релізом.
3. Зберегти чинні API/web image ID під rollback-тегами, приватну конфігурацію
   та попередній код. Змінити лише `PRODUCTION_OPERATOR_USER_IDS=[1]` у
   Compose `.env`; не змінювати прив'язку бота й unlimited allowlist.
4. Передати дозволений apps/infra набір без `.env*`, кешів і видалення
   серверних файлів. Зібрати API/web із production API URL, перевірити
   SDK і профіль. Зберегти встановлений overlay бота. Потрібна схема вже
   є; нових SQL-міграцій немає. Чинний deploy.sh повторює ідемпотентні 024–027.
5. Перезапустити API/web, перевірити шість служб, точні runtime hashes,
   HTTPS і права оператора. Зафіксувати доставлений маніфест та build ID.
   Жива перевірка нових маршрутів і правил видачі є умовою VERIFIED.
6. Створити запис M0-07 для вже наявної роботи №5. Таня сама підтверджує
   конкретний запуск; цей реліз не натискає генерацію від її імені.

Відкат: повернути попередні API/web образи, код і приватну конфігурацію,
використати обидва Compose-файли та `up -d --no-deps api web`; перевірити
HTTPS, бота й поточні права. Нова схема не вводиться, тому база не
відновлюється поверх живих даних заради відкату коду. Її відновлення —
окрема операція з погодженою точкою відновлення та зупиненням записів.
