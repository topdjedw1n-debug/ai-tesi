Дата: 05.09.2026. Статус: **LOCAL**.

Зміни не закомічені й не випущені на робочий сайт.
[Машиночитні докази та маніфест коду](M0-03-2026-09-05.json).

## Перевірений дефект і результат

До зміни обидва ручні detector gates приймали `22% + decision=passed`;
`editorial_review` допускав адміністративний override без no-rewrite.
Три регресійні перевірки відтворили саме ці порушення перед реалізацією.
Після зміни вони проходять у повному наборі API-тестів.

Чинна серверна політика: `agency-docx-2026-09-04`.
Для видачі потрібні Compilatio similarity ≤10% та AI ≤10%, збережені
звіти того самого фінального DOCX, явний огляд менеджером без переписування
та чинні внутрішні quality gates. Старий `passed` і довільний `report_ref`
не заміняють повного доказу за цією політикою.

## Що реалізовано

- `release_policy.py` повторно обчислює статус за числом і версією правил.
  Нескінченні значення, bool, рядки замість числа, пропуски та значення
  поза 0–100 відхиляються. Рівно 10 проходить; 10.0001 уже не проходить.
  Менеджер може відхилити прийнятний відсоток, але не прийняти завищений.
- Звіти PDF/PNG/JPEG до 20 MiB зберігаються окремими UUID-об'єктами
  у чинному файловому сховищі. `DocumentProvenance` зберігає автора,
  час, справу, SHA-256 звіту, fingerprint DOCX та версію політики.
  Це не source pack. Upload/list/download доступні лише за правами M0-02;
  storage path не повертається у публічній схемі метаданих звіту.
- Форма передає очікуваний fingerprint. Заміна DOCX після відкриття
  форми дає 409. Відсутній, чужий, застарілий, недоступний або змінений
  звіт не дає PASS. Обидві перевірки мають стосуватися саме DOCX.
- Огляд змісту зберігається в історії: `accepted`, `rejected` або `rewritten`.
  Прийняття означає відповідність завданню та `no_rewrite_confirmed=true`.
  Зафіксоване переписування є незворотним провалом цього результату;
  зміна хвилин, закриття редакторської задачі або повторна галочка його
  не стирають. Нове завершення генерації потребує нового огляду, а попередній
  провал залишається в історії. Override не заміняє огляд.
- Оновлення результатів/огляду відкликає дозвіл. Видача й завантаження
  перевіряють актуальні докази під блокуванням рядків document → case.
  SHA-256 обчислюється також із фактичного буфера, який повертається
  користувачу: окремий пізніший потік зі сховища не може підмінити байти.
  Імена завантажуваних файлів підтримують UTF-8.
- У кабінеті додано прикріплення й отримання звіту, два числові результати
  з явним підтвердженням відповідності DOCX та огляд змісту. Прибрано
  початковий шлях до RUN-001 і ручний перемикач зеленого статусу.
- Звіти включено до наявного очищення файлів при видаленні документа
  або облікового запису. Нової таблиці чи міграції не потрібно.

Два PostgreSQL-тести пропускаються без `M0_03_TEST_DATABASE_URL` у звичайному
ізольованому pytest і виконані окремо на тимчасовій базі. Тест створює
унікальну схему та видаляє лише її. Інші пропуски не зараховані як PASS.

Матриця API включає точний поріг для обох показників; невалідні числа;
стару політику/ручний PASS/override; відсутній і змінений звіт; чужу справу;
PDF замість DOCX; застарілу відкриту форму; обов'язковий огляд; стійке
переписування; нову генерацію; відкликання старого посилання; зміну байтів
під час отримання; видалення файлів звіту разом із власником. Доступ manager1
перевірено для всіх нових операцій; чужі ID не відкривають дані.

## Браузерний сценарій

Локальний web на `localhost:3103`, API на `localhost:8303`, окрема SQLite
та тимчасовий MinIO. Використано синтетичного manager1, власну справу №1
з документом №101 та чужий документ №102. Це не production account/session.
DOCX містить тестовий текст; PDF явно позначено `LOCAL TEST FIXTURE`,
`Not a real Compilatio report or M1 proof`.

Перевірено через браузер:

1. Звичайний парольний вхід і лише власна справа у списку.
2. Отримання внутрішнього DOCX; прикріплення PDF через справжній file chooser;
   поява звіту у двох формах та повторне завантаження тих самих байтів звіту.
3. 22% similarity збережено як failed, дозвіл заблоковано.
4. 10% similarity та 10% AI пройшли; без огляду дозвіл залишався заблокованим.
5. Явне прийняття без переписування → дозвіл → завантаження зі сторінки роботи.
6. Переписування з причиною → відкликання дозволу; після reload немає
   форми повторного прийняття, стан залишився failed/not_ready.

Обидва фактично завантажені DOCX мають 36 682 байти та SHA-256
`f3c78eb6f9c62dcb11a79c7538b441bbcd6dcb9e0fccb281328dea5e62dffc32`.
Перевірено самі файли з браузерного завантаження, не лише HTTP 200.
[Знімок стійкого блокування](M0-03-2026-09-05-rewrite.png).

Браузерний цикл передував останньому коригуванню типізації legacy
SQLAlchemy-присвоєнь; поведінка не змінювалася. Повний фінальний pytest,
PostgreSQL, Ruff і mypy виконані після цього коригування; фінальні SHA
збігаються з поточним кодом.

## Межі доказу та передача наступній задачі

- Compilatio залишається ручною зовнішньою перевіркою. Збереження та hash
  доводять цілісність доказів; справжність звіту, його відповідність
  перевіреному DOCX і правильність введених чисел підтверджує менеджер.
- Робочий сервер, база, права, паролі та реальна чернетка №5 не змінювалися.
  Платної генерації та повідомлень Тані/клієнтам не було. Нові production
  read probes не виконувалися; попередній живий знімок залишається M0-02.
- Збережено сторонні зміни й staging area. Моделі, міграції та
  `PHASE0_READINESS_RECORD.md` не переписувалися.
- M0-05: узгодити raw/англійські підписи, `delivered` відразу після дозволу
  та «Немає даних» для зовнішніх детекторів на сторінці документа, коли
  результати вже записані у справі. Під час початкового входу були два
  `Failed to fetch` для dashboard-запитів із подальшим відновленням;
  весь браузерний console не оголошується чистим. Це потрібно перевірити
  в повному сценарії M0-05, а не приховувати успіхом форм M0-03.
- M0-06: незалежне рев'ю, backup/restore та погоджений спільний API/web
  реліз. Старі ручні докази не мігруються в PASS автоматично. Старий web
  із `report_ref` несумісний із новим доказовим запитом; потрібен спільний
  реліз. При відкаті видачу слід призупинити: старий код не забезпечує
  еквівалентних правил. VERIFIED потребує перевірки доставленої версії.
- Продуктовий PASS M1 потребує реальної прийнятої роботи з Compilatio.
  Локальна синтетична перевірка ним не є.

Наступний конкретний крок — **M0-04**: перевірити поточний добір джерел
без PDF, його відновлення та блокування написання секцій до перевіреного
пакета. Уже існуючий конвеєр не переписувати. Нових уточнень фаундера
для початку цієї задачі немає.
