## Штатний цикл для наступних замовлень

Для вже завершеної №7 починати з перегляду файла й доказів (крок 6).
Внесені результати не дублювати; новий файл завжди має власні перевірки.

1. Увійти на [робочий сайт](https://app.thesica.co/auth/login) під manager1.
   Використовувати звичайний вхід, а не сторінку входу адміністратора.
2. У «Мої роботи» відкрити потрібне замовлення. Звірити тему, тип,
   обсяг, APA й вимоги. Історичні невдалі роботи не дублювати навмання.
3. Переглянути умови та припущення. Системна справа створюється під час
   запуску; вручну дублювати замовлення в іншій формі не потрібно.
4. Після перевірки умов менеджер підтверджує запуск. Авторизація Тані
   вже надана фаундером у AGENT_SYNC §14; повтор погодження не потрібний.
5. Очікувати готовий результат у цій роботі. Технічну причину остаточного
   збою визначає та усуває виконавець; повторювати її навмання не потрібно. При тимчасовому збої
   система відновить поточну спробу зі збереженими розділами; новий запуск
   натискати не потрібно. Після остаточної зупинки кнопка «Підтвердити нову
   спробу» доступна лише після підтвердження усунення причини й умов.
   Це нова платна спроба, яка замінює попередні частини та перевірки.
   Telegram-помічник уже прив'язаний до цього облікового запису.
6. Коли DOCX готовий, натиснути «Перевірка та видача цієї роботи» й
   отримати **DOCX для Compilatio**.
   Це внутрішній файл для перевірки. Сама наявність файла ще не означає
   дозволу віддати його клієнту.
7. Перевірити зміст і провести обидві перевірки Compilatio на цьому самому
   незміненому DOCX. Зберегти обидва звіти або звіт з обома показниками.
8. У блоці «Звіти Compilatio» вибрати справжній звіт — PDF, PNG або JPEG
   до 20 МБ — і натиснути «Прикріпити звіт». Якщо звіти окремі, прикріпити
   обидва. Їх можна знову завантажити через назву файла. Копіювати технічні
   ідентифікатори або редагувати документи проєкту не потрібно.
9. У формах «Збіги тексту (similarity)» та «Показник AI» внести точний
   відсоток, вибрати прикріплений звіт, перевірити час і підтвердити, що
   звіт та число стосуються саме цього DOCX. Зберегти обидва результати.
   Система сама застосовує поріг: будь-який показник понад 10% блокує
   видачу. Якщо файл змінився, потрібна нова перевірка й актуальний звіт.
10. Відкрити DOCX у Word або LibreOffice з погодженим оформленням. Звірити
    обсяг із завданням і ввести фактичну кількість сторінок у «Огляд змісту
    менеджером». Число слів на сайті не замінює перевірки сторінок. Обрати
    рішення після читання роботи. Прийняти можна лише роботу, яка відповідає завданню і не потребувала
    переписування змісту. Якщо знадобилося переписування — зазначити це
    та описати причину. Таке рішення не стирається повторною галочкою.
11. Коли обидва показники ≤10%, огляд прийнято й інші перевірки пройдені,
    натиснути «Дозволити видачу» у справі, потім «Завантажити перевірений
    DOCX». Файл також доступний зі сторінки роботи через «Завантажити DOCX».
    Це саме перевірений файл; зміна файла
    або доказів відкликає дозвіл. Дозвіл ще не означає передачі клієнту.

Перший короткий прогін має запис SHORT-001, підготовлений у M0-07. RUN-001 призначений
для повних робіт M2 і не є заміною звіту Compilatio.

Ще два різні замовлення на 10–20 сторінок Таня добирає для послідовності
M1. Перша чернетка вже вибрана, тож їхня відсутність не потребує
повторного введення роботи №5.

## Активація для виконавця релізу

Цей розділ є технічною інструкцією, а не діями для Тані.

Наведену нижче активацію виконано 07.09.2026 у M0-06. Не повторювати
без зміни стану; фактичні докази й межі діагностичного входу — у релізному звіті.

- Джерело прав: `Settings.PRODUCTION_OPERATOR_USER_IDS`, за замовчуванням
  `[]`. Для підтвердженого manager1 встановити `[1]` у джерелі змінних
  Docker Compose погодженого релізу. Поле явно передається в `api.environment`;
  значення лише в bot `api.env` не перекриє його. Перед застосуванням
  перевірити resolved Compose environment, не друкуючи секрети.
- Потрібний реліз API **та web**, включно з новими manager routes;
  лише зміна змінної без нового коду недостатня. Не використовувати
  локальну `.next` збірку з localhost API як production-артефакт.
- Нової схеми, прав адміністратора, скидання пароля або нової Telegram-
  прив'язки не потрібно. Зберегти наявні bot mapping, unlimited-generation
  exemption і всі чинні quality gates.
- До релізу: незалежне рев'ю відповідного diff M0-02..05, актуальний
  backup і план відкату за [релізною процедурою](PRODUCTION_DEPLOYMENT_PLAN.md).
  Реліз погоджує фаундер; новий реліз у M0-02 не виконувався.
- Canary: звичайний вхід manager1; `/auth/me` повертає
  `can_access_production=true`; видно тільки її документи/справи;
  працюють список і деталі, чужі ID та адміністративні дії повертають
  403/404. Порожній DOCX дає FILE_NOT_READY, а не фіктивний download/PASS.
- Правила M0-03 перевіряти на окремій ізольованій справі: 22% блокує;
  10%/10% без огляду блокує; з оглядом дозволяється той самий DOCX;
  переписування відкликає дозвіл і не стирається. Не записувати тестове
  переписування в реальну першу роботу Тані.
- Автоматичне створення справи вже виконується endpoint першого повного
  запуску. Не створювати дубль для document_id=5. Перевірити прямий перехід
  із документа до власної справи, відновлення статусу після reload та
  обов'язкове `reviewed_page_count` для нового прийнятого огляду.
- Зібраний у M0-05 web містить localhost API і призначений лише для
  ізольованої перевірки. Під час релізу зібрати web із робочою адресою API.
- Відкат доступу: повернути allowlist до попереднього значення та
  відновити погоджену версію API/web, зберігши документи, справи й докази.

Технічний доступ M0-02 активовано й перевірено 07.09.2026; особистий вхід
Тані ще потребує її підтвердження. Код M0-05 встановлено, а розуміння
повного процесу Танею приймається на реальній роботі. Готова прийнята
робота доводиться реальним прогоном, не цим checklist.
