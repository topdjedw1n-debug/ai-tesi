# Контракт «кабінет менеджера ↔ виконавець генерації»

**09.09.2026 · Автор: Fable. Статус: ПОГОДЖЕНО фаундером 09.09.2026; здійсненність
підтверджена Codex ([записка](../evidence/CONTRACT-CABINET-EXECUTOR-FEASIBILITY-2026-09-09.md)), доповнення 1 нижче.** Крок 1 [плану перебудови](THESICA-REBUILD-EXECUTOR-2026-09-09.md).
Контракт описує, що кабінет показує і що виконавець зобов'язаний віддати.
Він не описує, як виконавець пише текст (це специфікація кроку 2).

Принцип: наявні маршрути API і таблиці зберігаються; контракт додає поля й
звужує стани. Нових таблиць не потрібно; нові структури — JSON у наявних
записах job / provenance / production case.

## 1. Шлях менеджера

1. Створює чернетку: тема, тип і рівень роботи, мова, обсяг, вимоги, за
   бажанням PDF (методичка, джерела). Маршрути наявні.
2. Бачить завдання і припущення системи, підтверджує їх (task-contract).
   Без підтвердження запуск неможливий. Наявне.
3. Запускає генерацію однією дією. Повторне натискання під час активної
   роботи повертає 409 і не створює другого job.
4. Спостерігає прогрес; може скасувати.
5. Отримує результат: завжди або DOCX із попередженнями, або технічну
   зупинку з однією наступною дією.
6. Завантажує DOCX, проводить Compilatio, вносить результат, дає дозвіл на
   видачу. Маршрути видачі й гейти релізу наявні і цим контрактом не
   змінюються.

## 2. Стани роботи (job)

Рівно п'ять: `queued` → `running` → `completed` | `failed` | `cancelled`.
`completed`, `failed`, `cancelled` — кінцеві. Нова спроба = новий job.
`failed_quality` для нових робіт не існує: якість не зупиняє генерацію.
`failed` означає лише технічний стоп із §4.

Статус документа й `generation_status` справи дзеркалять job: `queued`,
`generating`, `completed`, `failed`, `cancelled`. Стани `outline_generated`,
`sections_generated`, `payment_*` кабінет для нових робіт не показує.

## 3. Прогрес (`GET /jobs/{job_id}/status`, наявний маршрут)

Наявні поля лишаються: `job_id`, `status`, `progress` (0–100),
`document_id`, `error_message`, `attempt_count`, `started_at`, `heartbeat_at`,
`observed_at`. Додаються:

| Поле | Значення |
|---|---|
| `stage` | одне з `sources`, `outline`, `writing`, `references`, `assembling` |
| `stage_label` | українська назва етапу для кабінету |
| `sections_done`, `sections_total` | лічильник розділів на етапі `writing` |
| `last_signal` | останнє повідомлення виконавця людською мовою, ≤ 120 символів |
| `cost_cents_so_far`, `tokens_so_far` | накопичений облік застосунку |
| `warnings_count` | кількість попереджень на цей момент |

Heartbeat під час `running` оновлюється не рідше ніж раз на 60 с, зокрема
під час очікування відповіді моделі. Якщо heartbeat старший за 5 хвилин,
кабінет показує «виконавець не відповідає» і адміністративну дію.

## 4. Технічні стопи (`status = failed`)

Замість рядка помилки — структура `stop`:

| Поле | Значення |
|---|---|
| `code` | `provider_access` (доступ/кошти провайдера), `provider_unusable_response` (після обмежених повторів немає придатної відповіді на обов'язковому кроці), `storage_or_db` (не читається вхід або не записується прогрес/файл) |
| `message_uk` | що сталося, людською мовою |
| `next_action` | `retry_now`, `retry_after_owner` (потрібна дія власника: баланс, доступ), `contact_owner` |
| `retryable` | чи має сенс кнопка «Нова спроба» |
| `stage`, `section_index` | де сталося |

Інших дозволених кодів стопу немає. Невідома помилка коду отримує
`code = internal_error`, `next_action = contact_owner` і завжди вважається
дефектом виконавця, а не дозволеним станом. Скасування менеджером =
`cancelled`, без `stop`.

`error_message` зберігається для сумісності і дорівнює `stop.message_uk`.

## 5. Попередження (`generation_warnings` у справі, наявне поле)

Список записів:

| Поле | Значення |
|---|---|
| `code` | із закритого переліку специфікації кроку 2 (наприклад `source_coverage_gap`, `reference_replaced`, `standard_reference_used`, `outline_review_negative`, `claim_unsupported`, `detector_unchecked`, `output_truncated_retried`) |
| `severity` | `info` або `warning` |
| `stage`, `section_index` | де виникло |
| `message_uk` | одне речення для менеджера |
| `detail` | обмежені дані для розбору, ≤ 1000 символів |
| `created_at` | час |

Кабінет показує попередження у справі списком, згрупованим за розділами,
з підсумком «N попереджень» у списку робіт. Попередження ніколи не
зупиняють генерацію і не змінюють `status`. Формулювання «потребує
перевірки менеджером» у кабінеті немає.

## 6. Результат (`status = completed`)

Виконавець зобов'язаний віддати все з цього переліку; відсутність будь-чого
= дефект виконавця, не стан.

| Артефакт | Вимога |
|---|---|
| DOCX | цілісний файл, SHA-256, розмір, оцінка сторінок; доступний одразу через наявний маршрут експорту/завантаження |
| Розділи | назва, кількість слів, порядок; збережені окремо від DOCX |
| Бібліографія | кожен запис: ключ, форматоване посилання, `verified = true`, джерело перевірки (Crossref/OpenAlex/Semantic Scholar/arXiv/каталог книг/WHO/PDF); неперевірених записів у DOCX немає |
| Джерела | список використаних із позначкою, чи з пакета, з PDF, чи зі стандартної бібліотеки |
| Облік | токени й центи за кожним зверненням до моделі та сумарно |
| Запис | ідентифікатор повного запису прогону для відтворення |
| Попередження | повний список §5 |

Змінений текст або посилання = новий DOCX з новим SHA; попередні перевірки
Compilatio до нового файла не застосовуються (наявне правило видачі).

## 7. Дії менеджера (маршрути наявні)

| Дія | Маршрут | Умова |
|---|---|---|
| Запуск | `POST /generate/full-document` | підтверджене завдання; немає активного job; інакше 409 |
| Скасувати | `POST /generate/full-document/{id}/cancel` | лише `queued`/`running`; завершується протягом 60 с навіть під час очікування моделі |
| Нова спроба | той самий запуск після `failed`/`cancelled` | одне підтвердження; попередні розділи не втрачаються, але нова спроба пише заново |
| Завантажити DOCX | наявний експорт | будь-який `completed` |
| Compilatio | `POST /production-cases/{id}/detector-reports` | прив'язка до SHA файла, наявне |
| Дозвіл на видачу | `POST /production-cases/{id}/release` | наявні правила §4 брифу без змін |

Дії, які прибираються з кабінету для менеджера: редакторські задачі,
оплати, тарифи, «повторний запуск із тим самим job».

## 8. Інваріанти

- Один активний job на документ. Бриф, вимоги, підтверджене завдання і
  завантажені PDF незмінні на час job.
- Старі роботи №1–№11 та їхні job не переоцінюються і не мігрують у нові
  стани; кабінет показує їх за старими мітками.
- Кожне звернення до моделі записане до розбору відповіді; `completed`
  без запису неможливий.
- Кабінет отримує стан лише через `GET` статусу та справи (опитування, як
  зараз); виконавець не пише в UI напряму.
- Усе, що кабінет показує менеджеру, є в українській мові в полях
  `*_label` / `message_uk`; кабінет не перекладає коди сам.

## 9. Що потрібно змінити (оцінка для Codex)

- API: розширити відповідь статусу job (§3), додати `stop` (§4), закріпити
  схему попереджень (§5), гарантувати перелік результату (§6). Без нових
  таблиць: `stop`, `stage`, лічильники — у JSON job; попередження і
  бібліографія — у provenance/справі, як зараз.
- Кабінет: показ етапу, лічильника розділів, останнього сигналу, стопу з
  однією кнопкою, списку попереджень; прибрати `failed_quality`, редакторські
  задачі, оплати для менеджерського шляху.
- Codex повертає: перелік файлів, які зачіпає контракт, і що з нього
  нездійсненне на наявних маршрутах без міграції. Це і є перевірка кроку 1.

## Доповнення 1 — після перевірки здійсненності Codex (09.09.2026)

1. **Підтвердження завдання обов'язкове завжди**, і за наявності методички.
2. **Повторний запуск під час активного job → 409**, зокрема для того самого
   наміру; поточна поведінка «200 з наявним job» для v2 не застосовується.
3. **Нова спроба = новий job.** Термінальний job незмінний; `/resume` для v2
   не використовується. Перед новою спробою попередні розділи, джерела і
   план зберігаються повним незмінним знімком у provenance з
   `previous_job_id`; видалення попередніх розділів без знімка заборонене.
   Міграція для рядків розділів за job не потрібна.
4. **Скасування** → документ і справа `cancelled`; активний стан справи
   `generating`. Нові проєкції лише для v2; старі роботи не переписуються.
   Кабінет читає стан через `GET` і показує `*_label`/`message_uk` з API;
   власний переклад кодів і WebSocket-канал прибираються.
5. **Точні маршрути** (усі під `/api/v1`): справи —
   `/admin/production-cases/...`, включно з `detector-reports` і `release`;
   числа Compilatio —
   `POST /admin/production-cases/{id}/release-gates/{gate_key}/detector-result`;
   DOCX до видачі — `POST /admin/documents/{document_id}/download` з
   виробничим доступом; звичайний export лишається після видачі.
6. **Стандартні посилання**: перевірка й заміна до DOCX — реалізація v2
   (специфікація §S5), формат БД достатній.
7. **Недоступна БД**: стоп/скасування записуються після відновлення; кабінет
   показує недоступність за heartbeat. Скасування не перериває вже
   надіслане звернення до провайдера: пізня відповідь записується і
   ігнорується.
