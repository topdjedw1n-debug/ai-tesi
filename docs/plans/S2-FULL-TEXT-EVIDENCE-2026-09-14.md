## 0. Ціль і критерій кроку

Той самий писар з тією самою виробничою інструкцією, але з повними входами, дав на розділах B 0–11 % AI проти 19–39 % (М1). Крок 1 робить «повні входи» штатною частиною конвеєра, без платних прогонів:

1. джерело в пакеті — набір **фрагментів одного документа з номерами сторінок**, а не один блоб на 2 400 символів;
2. розділ отримує **лише релевантні йому фрагменти** (за планом S3: назва, purpose, main_points, терміни scope);
3. S5 будує бібліографію **на документ**; ключів фрагментів немає взагалі, отже й двокрапки;
4. правило цитування для similarity — у промпті S4, лише коли є повнотекстові докази;
5. повні тексти надходять трьома шляхами: завантажені менеджером PDF (уже є), відкриті PDF автоматично (нове), нормативні акти й рішення — у кроці 1 через завантаження (див. §3).

Критерій кроку 1: повні тести API і web зелені; точні відтворення job15/16/17/18 побайтові; сухий прогін лабораторії на записі B показує промпт S4 із фрагментами, отриманими штатним кодом; офлайн-звіт показує, які фрагменти отримав би кожен з 24 розділів B. Крок 2 (повна робота B, ≈ $3 + ≈ 48 кредитів) — лише після окремого «так».

## 2. Модель даних: документ → фрагменти → розділ

- **Документ = один ключ пакета** (`K…` для знайдених, ключ файла для завантажених). Бібліографія, маркери `[K…]`, `pack_keys_used`, S5 — без змін. Фрагмент **не є ключем**: писар посилається `[K…] p. N` (наявна конвенція), а не на `[K…:3]`. Це прибирає двокрапку і проблему `[CASS25732]:3` з М1 за визначенням.
- **Фрагменти живуть у `pack.passages`** як `SourcePassage`: для завантажених файлів — як сьогодні; для відкритих PDF — `source_file_id=0`, `filename=<url>`, `citation_key=K…`, `page_number`, `text`. Розбивка — той самий `split_passages` (сторінка не перетинається, перекриття 150). Відбиток пакета вже покриває кожен пасаж.
- **Блоб `academic_evidence` (≤2 400) лишається** для S3 (огляд пакета в плані), для `evidence_text` (дозволені ключі, старі перевірки) і як запасний доказ; для джерел із фрагментами він складається з анотації + релевантних темі сторінок (як для завантажених сьогодні).
- **`canonical_metadata` джерела** отримує невелике зведення `full_text = {origin: "uploaded"|"open_access", url, pages, fragments, chars}` і `open_access_url` (якщо було); `evidence_level = "pdf"` для всіх джерел із фрагментами (завантажених і відкритих). Самі тексти сторінок у метадані не кладуться (рядок бази і подія пакета не роздуваються); повні сторінки відкритих PDF лежать у записаній залежності, з якої відтворення їх відновлює детерміновано.
- **Розділ отримує фрагменти на момент письма** (S4), а не в плані: план S3 і далі призначає документи (`evidence_keys`), а сторінки для розділу обираються лексично за запитом розділу. Довгий документ (норма, постанова, стаття) підтримує кілька розділів різними сторінками — це не можна знати в S3 на рівні документа.

## 3. Звідки беруться повні тексти

| Шлях | Крок 1 | Як | Що записується |
|---|---|---|---|
| Завантажені менеджером PDF | штатно (уже є) | сторінки → пасажі → фрагменти; для непублічних джерел, норм і рішень: менеджер зберігає текст як PDF (normattiva й сайти судів мають «друк у PDF») і завантажує; метадані (назва, автор-інституція, рік) править у картці файла | у `executor_inputs` |
| Відкриті PDF автоматично | нове | посилання приходить **у рядках пошуку** без додаткових звернень: OpenAlex `best_oa_location.pdf_url`, інакше `open_access.oa_url`; Semantic Scholar `openAccessPdf.url` (поле додається у `fields`); Crossref не дає ознаки відкритості — не використовується. Отримання — `httpx` з браузерним User-Agent, редиректи, ліміт 25 МБ, тайм-аут 30 с; якщо відповідь HTML — один перехід за `<meta name="citation_pdf_url">` (репозиторії, zenodo); далі `extract_pdf_pages`; сторінки без текстового шару → відмова | одна записана залежність `executor_full_text` на джерело: сторінки тексту (не байти PDF), або помилка |
| Нормативні акти, рішення, Garante — автоматично | **не в кроці 1** | normattiva віддає HTML (перевірено, 200) і має детерміновані URN для законів; для постанов Касації публічного стабільного API немає (третій сторони, JS). Автоматичний шлях потребує кроку «модель пропонує посилання → система їх отримує й тим підтверджує; що не отримано — не цитується» (як `[STD:…]` для книг). Це окрема робота після того, як крок 2 доведе ефект на повній роботі | — |

Перевірка на пакеті B ($0, 14.09): за OpenAlex 34 з 40 джерел відкриті; прямі PDF віддають EJPLT (5 статей) і Labour & Law Issues (unibo); FUP (`media.fupress.com`), IRIS-репозиторії за `hdl.handle.net`, Taylor & Francis відповідають 403 (Cloudflare) — вони отримуються лише через завантаження менеджером; zenodo дає PDF через `citation_pdf_url`. Отже автоматика дасть кілька повних текстів на пакет, а не всі; для решти — менеджер.

## 4. S2 (`executor_v2/sources.py`) — зміни

1. **Рядки пошуку несуть посилання на відкритий PDF**: `search_openalex`/`search_semantic_scholar` кладуть `canonical_metadata={"open_access_url": …}` у `SourceDoc`, коли API його дає. Записи старих прогонів такого поля не мають — для них нічого не змінюється.
2. **Злиття кандидатів** зберігає перше знайдене `open_access_url` серед рядків різних провайдерів (як зараз анотацію).
3. **Перевага при доборі — знята після рев'ю Astra** (§13): порядок кандидатів не змінюється; відкритість не є ознакою релевантності.
4. **Отримання після добору**: лише для відібраних (≤40) джерел із посиланням — `full_text(url)` (записана залежність) під тим самим семафором; успіх → пасажі через `split_passages` → `pack.passages`; блоб перезаморожується як анотація + релевантні сторінки; `full_text` і `evidence_level="pdf"` у метаданих. Невдача (403, HTML без PDF, скан) → джерело лишається на анотації.
5. **Попередження** (закритий словник, +1 код, рівень info, один раз на роботу): `source_full_text_unavailable` — «Повний текст частини джерел не вдалося отримати автоматично; використано анотації. За потреби завантажте PDF.» з переліком ключів у `detail`. Подія `executor_full_text` — результат на кожне джерело (сторінки, фрагменти, символи, статус).
6. Завантажені файли — без змін у S2 (їхні пасажі й так у пакеті).

## 5. S3 — без змін

Огляд пакета в промпті плану лишається `{key, title, evidence(блоб)}`. Для розділів S3 і далі обирає документи; сторінки обираються в S4. Це свідомо: (а) промпт S3 старих записів не змінюється; (б) знання про кількість сторінок у S3 не змінює плану; (в) релевантність сторінок можна порахувати лише маючи main_points розділу, які S3 сам і породжує.

## 6. S4 (`executor_v2/sections.py`) — відбір фрагментів на розділ

Нова функція поза пакетом, `app/services/full_text_sources.py: section_evidence(pack, section, scopes)` → (список `{"key","text"}` для промпту, звіт для події). Правила:

1. **Запит розділу** = назва + purpose + main_points + `terms_local`/`terms_en` вузлів scope цього розділу. Оцінка фрагмента — наявний `score_passage` (покриття термінів запиту + щільність), без моделі, детерміновано.
2. **Заплановані ключі (S3) — у тому самому порядку**: якщо документ має фрагменти — беруться найрелевантніші (вікна нижче половини найкращого бала документа відкидаються як баласт); якщо жоден фрагмент не набрав балу — заморожений уривок, як сьогодні, і позначка `gap` у звіті; якщо фрагментів немає — уривок байт у байт.
3. **Доповнення поза планом — лише завантажені менеджером документи**: документ додається після запланованих, якщо його найкраще вікно покриває власні слова розділу (назва, purpose, main_points) на ≥ 0,30 і ≥ 5 різними термінами. Так норма чи постанова, завантажена менеджером, доходить до розділів, де про неї йдеться, незалежно від здогаду S3 на рівні документа. Отримані автоматично тексти й джерела лише з анотацією поза планом не додаються (див. §13).
4. **Бюджети** (константи модуля, не `POLICY`): на розділ ≤ 20 000 символів доказів (≈ 5 тис. токенів; у М1 §20 мав ≈ 18 тис.), на документ ≤ 16 000; вікна роздаються по колу між документами розділу (найрелевантніше першим), тож короткий документ не голодує поруч із довгим, а довгий не обрізається до половини М1. Вибрані вікна впорядковуються за сторінкою; сусідні вікна тієї самої сторінки зшиваються без дубля перекриття; несуміжні лишаються окремими блоками, кожен з міткою `[page N]` — та сама форма, що в блобі завантажених файлів.
5. **Промпт**: структура та `S4_INSTRUCTION` без змін. Якщо серед доказів є хоч один повнотекстовий, після інструкції додається одне речення-правило (константа `FULL_TEXT_RULE`): дослівно цитувати сторінкові уривки лише короткими фразами; норми й рішення передавати посиланням і стислим переказом (звужено за рев'ю Astra, §13). Для записів лише з анотаціями промпт побайтово той самий — ось чому job15–18 відтворюються без змін. Правило умовне, бо стосується саме того, як користуватися повнотекстовим матеріалом; це не перемикач у налаштуваннях, а залежність від даних, як і сам список доказів.
6. **Подія** `executor_section_evidence` перед зверненням: для кожного ключа — заплановано/доповнено, сторінки, вікна, символи, найкращий бал. Повний текст доказів і так у записаному запиті S4.
7. `allowed`, `pack_keys_used`, обробка `[STD:…]`, обрізання — без змін.

Чому не «ключ на фрагмент», як у М1: (а) бібліографія на документ — автоматично; (б) двокрапки й `[KEY]:3` немає; (в) локатор `p. N` — і академічний апарат сторінки (те «зерно», яке Astra і Grok бачать у людських текстах), і чинна конвенція інструкції; (г) S5 не змінюється. М1 доводив ефект матеріалу, а не форми ключів: писар бачив ті самі тексти.

## 7. S5 і форматування

- Бібліографія і заміна маркерів — без змін: один запис на ключ документа.
- `[K…] p. N` рендериться як сьогодні: «(Автор, рік) p. N». Згортання сторінки в дужки — косметика S5 на потім (у записі B є одне таке місце; правка змінила б DOCX B, тому не в кроці 1).
- Інституційні автори: `_institutional_author` у форматері не знає «Corte», «Cassazione», «Repubblica», «Garante», «Parlamento», «Commissione», «Consiglio», «Autorità», «Court», «Parliament», «Commission» — зараз «Corte di Cassazione» стало б «(Cassazione, 2021)», «Repubblica Italiana» — «(Italiana, 1970)». Додаю ці слова до регулярного виразу: потрібно для крок 2 (норми й рішення як завантажені PDF), у старих пакетах таких авторів немає — відтворення не змінюється. Повноцінний стиль цитування правових джерел (l. n. 300/1970, art. 4; Cass., sez. lav., …) — окрема робота після кроку 2.

## 8. Відтворення і межі змін

- Старі записи (job15/16/17/18): рядки пошуку без `open_access_url` → без отримання → пакет, S3, промпт S4 (без `FULL_TEXT_RULE`, докази — блоби) побайтово ті самі. Доказ — точне відтворення чотирьох записів після змін (§13).
- Нові записи: `executor_full_text` записується на кожне відібране джерело з посиланням; відтворення відновлює сторінки зі стрічки без мережі.
- Пакет `executor_v2` лишається ≤ 1 500 рядків: новий код живе в `app/services/full_text_sources.py`; з `run.py` виноситься чиста побудова рядків завантажених файлів у `uploaded_sources.py` (той самий результат). Перемикачів немає; `POLICY` і перелік моделей не змінюються (нові константи — у модулі повних текстів).
- База даних: без міграцій. Нових колонок немає; `canonical_metadata` — наявний JSON.

## 9. Лабораторія і доказ за $0

Розширення `apps/api/scripts/s4_lab.py` (поза виробничим кодом):

- `--uploaded-sources FILE.json` — список `{pdf, key, title, authors, year, mandatory, url}`: PDF розбираються штатними `extract_pdf_pages`/`split_passages` і додаються у записаний вхід `executor_inputs` як завантажені менеджером файли. Це підміна **входу** (як якби менеджер завантажив файли), а не коду: S2, відбір фрагментів і промпт S4 — штатні.
- `--recorded-outline` — план S3 береться зі стрічки, хоча запит S3 змінився (у пакеті з'явилися завантажені джерела). У звіті `request_changed: true` для S3 і сам прапорець. Без цього будь-який новий вхід означає живий S3 і живий запис усіх розділів (≈ повний прогін).
- `--allow-host HOST` — дозволені хости для отримання відкритих PDF у live; нова залежність `executor_full_text`, якої немає на стрічці, іде наживо (як `verify` для нових `[STD:…]`).

## 11. Ризики і межі

- **Лексичний відбір** — не семантичний: англомовні джерела під італійський запит отримають мало балів (спільні лише GDPR, privacy, data…). Для запланованих S3 ключів це м'яко (запасні перші вікна); для доповнення — такі джерела не додаються. Семантичний відбір (ембеддінги) — не зараз: спершу побачити, чи лексичного досить на B (офлайн-звіт це покаже за $0).
- **Шум доповнення**: поріг 0,25 — перша оцінка; калібрується офлайн на B (норма й постанова мають потрапити в §4, §6, §14, §18, §20, а не у §8 про історію GDPR). Якщо калібрування не вдається — доповнення лише для файлів `mandatory` (менеджерське рішення) — рішення після звіту.
- **Similarity**: дослівні норми індексуються (М1: 3–15 % на коротких файлах). Правило в промпті знижує ризик, але не гарантує; дешевий наступний запобіжник — дорадча міра дослівного збігу розділу з його доказами (n-грами) як попередження. Не в кроці 1: спершу один повний файл і скан.
- **Cloudflare/платні**: частина відкритих посилань не віддає PDF (FUP, IRIS, T&F). Це фіксується подією і попередженням; шлях — завантаження менеджером.
- **Розмір записів**: сторінки відкритих PDF у залежності (≈ 100–300 тис. символів на статтю, до 40 джерел) — записи виростуть на одиниці МБ; прийнятно (запис smoke був 15,5 МБ).
- **Мовні уламки**: англійські фрагменти в італійському тексті — та сама небезпека, що з анотаціями (Grok); інструкція незмінна, тож ризик лишається; дивитися на повній роботі.

## 13. Рев'ю Astra (14.09, до коду) і що змінено в проєкті

Astra (`codex exec -m gpt-6-astra -s read-only`, xhigh, ізольована тека з проєктом, фактами й кодом S2/S4/S5, 73 635 токенів): **напрямок — доцільно зараз, обсяг звузити**; центр кроку 1 — перенести у штатний конвеєр якість *ручного* добору фрагментів М1, а не лише механіку. Прийняті правки:

1. **Перевагу відкритих PDF при доборі знято**: відкритість не виправляє релевантність (у пакеті B є геодезія моста й стічні води).
2. **Доповнення поза планом — лише для завантажених менеджером документів**; отримані автоматично повні тексти працюють там, де їх призначив S3 (їхню релевантність ніхто не перевіряв). Поріг — за власними словами розділу (назва, purpose, main_points), не за термінами scope: калібрування на B показало, що короткий англійський запит («remote monitoring») дає 0,5–0,6 сторонньому англомовному документу про моніторинг моста; за словами розділу той самий документ дає 0,0. Порог 0,30 і ≥5 різних збіглих термінів (§14).
3. **Бюджети — по колу між документами** (кожен документ отримує мінімальну частку, потім розширення), ліміт на документ 16 000: десять фрагментів постанови з М1 не обрізаються.
4. **Запланований документ без релевантного вікна отримує свій заморожений уривок** (ніколи не менше, ніж сьогодні) і позначку `gap` у звіті, а не «перші два вікна» (титул/вступ).
5. **Правило цитування звужено** до короткої дослівної цитати й переказу з посиланням; вимогу «будувати аргумент на положеннях» прибрано, щоб не змінювати умови письма понад М1.
6. **Дублі**: знайдений запис завантаженої роботи вилучається з добору (`sources_equivalent`, як у збереженні пакета) — без цього завантаження Ghionzoli поруч зі знайденим Ghionzoli зупиняло роботу помилкою «duplicate publication» (виявлено сухим прогоном).
7. **Відтворюваність — доведена, а не заявлена**: чотири точні відтворення після змін і тест відтворення нового отримання без мережі, включно з відмовою 403 і транспортною помилкою (§14).
8. Мовні запити розділено: локальний (план + terms_local) і англійський (terms_en); вікно оцінюється найкращим збігом.

Не прийнято зараз: семантичний відбір, розширення локаторів до статей/пунктів (номер сторінки PDF — єдиний локатор кроку 1; для норм і рішень стаття/пункт видно в самому тексті вікна), перевірки тверджень на тих самих вікнах (S4b — після кроку 2). Крок 2 оцінюється лише за планкою власника (≤10 % обидва + зміст); «нижче 33 %» — не критерій, а опис покращення без проходження.
